# Read API gaps for the frontend

Source review: 2026-09-23. These are **proposed contracts**, not registered routes. The frontend never calls them. Existing backend files were not changed. Source evidence takes precedence over older audit findings and simplified examples.

**Backend status update (2026-09-23, added by the backend session(s) that read this doc):** every item in this document is now closed. Items 1–7 are fully implemented — `GET /v1/analytics/summary`, usage-observation `source`/`kind`/`usage_canonical` (the `kind` question resolved by checking actual provider behavior, not left as an open model), the `providers/comparison` usage-multiplication fix, `GET /v1/analytics/costs`, request-detail's new `routing`/`errors`/`costs` sections + attempt spans + per-choice generation rows + cursor-paginated timeline, keyset pagination + new filters for `GET /v1/analytics/requests`, and the `fallbacks` request-scoping fix, respectively. Item 8 is implemented for its persistence-health half only (`GET /v1/analytics/persistence`) — its auth half was explicitly declined by the user for this personal, loopback-only deployment, not deferred. See each item's own status note below for exact shape and any deviation from the original proposal, and `docs/REMEDIATION_PLAN.md`'s latest status block for the full account. Note item 6 is a **breaking change** to `requests`' pagination contract (`offset` removed in favor of `cursor`) — update any existing frontend usage accordingly.

## 1. Historical summary and series

**UI need:** a date-aware usage/activity view with comparable populations.

**Evidence:** `src/server/routes/analytics.rs` only accepts model/provider/success/limit/offset for request lists. `/metrics` holds process counters. There is no date-aware aggregate route.

**Proposed:** `GET /v1/analytics/summary?from=<UTC>&to=<UTC>&bucket=minute|hour|day&model=&provider=` returns `{scope:{from,to,bucket,provider_semantics},requests:{total,successful,failed,pending},attempts:{total,failed},usage:{prompt,completion,cached,reasoning,known_requests,eligible_requests},series:[...]}`. Use a half-open `[from,to)` interval, UTC bucket boundaries, bounded maximum buckets and explicit final-serving-provider semantics. Unknown usage is null, never zero; aggregate at request/attempt grain before joining.

**Acceptance:** seed boundary timestamps, retries, failed and pending requests, absent usage and repeated updates. Verify correct grain, UTC boundaries and coverage without multiplying requests or summing cumulative usage.

**Status (2026-09-23): implemented as proposed.** `GET /v1/analytics/summary?from=&to=&bucket=&model=&provider=` — see `docs/API_REFERENCE.md` §8. Matches the proposed shape exactly, including `provider_semantics`, null-not-zero usage, and canonical (most-recent) usage de-duplication before summing. One addition beyond the original proposal: a 500-bucket cap returning `400 range_too_large` if exceeded (the "bounded maximum buckets" requirement, made concrete). Tested end-to-end in `tests/analytics_tests.rs::analytics_summary_covers_boundaries_retries_pending_and_usage_dedup`, which seeds exactly the acceptance scenario above (boundary timestamps at both ends of the half-open window, a retry chain, a pending request, a failed request with no usage, and a request with two cumulative usage updates) against a real Postgres.

## 2. Usage observation identity and finality

**UI need:** trustworthy request totals, cached share, and timing sample counts.

**Evidence:** `UsageRecorded` always inserts in `src/telemetry/writer.rs`. `stream_instrumentation.rs` emits every usage update and converts absent primary counts to zero. Detail returns only attempt number and numeric fields; no timestamp, observation ID, final marker, or raw-provider usage. Multiple rows can be cumulative updates, not separate generations. This is a current source limitation, not merely legacy telemetry.

**Proposed detail extension:** usage rows include `{id,attempt_number,observed_at,kind:delta|cumulative|final,source,counts:{prompt:number|null,completion:number|null,total:number|null,cached:number|null,reasoning:number|null}}`; response includes an independently derived canonical final record per attempt and quality/coverage flags. Preserve raw observations.

**Acceptance:** duplicate/reordered cumulative updates and missing final updates never inflate totals; zero remains distinguishable from missing; invalid subsets are flagged. Until then the frontend displays observations separately and does not sum them.

**Status (2026-09-23): implemented, with the `kind` question resolved by research rather than left open.** The question of whether `kind` needed to model `delta|cumulative|final` was answered by checking what this gateway's actual supported providers do: OpenAI, OpenRouter, llama.cpp/llama-server, vLLM, Ollama, and Gemini's OpenAI-compat layer all follow the same documented convention — one usage object per attempt, reporting a cumulative total for the whole response, delivered either in the final SSE chunk (`stream_options.include_usage`) or the single non-streaming response body. None of them stream incrementally-increasing per-chunk deltas. So `kind` is always `"cumulative"` today; it's still a real column (not a hardcoded constant) so a future non-conforming provider could be represented without another schema change, but there is no live `delta`/`final` distinction to build against real provider behavior right now.

New migration `007_usage_observation_provenance.sql` adds `generation_usage.source` (`"stream_final"`/`"non_streaming"`, set from `InstrumentedStream`'s existing `synthetic` flag) and `.kind`. `GET /v1/analytics/requests/{id}` now returns both the raw `usage` array (unchanged in shape, preserving every observation) and a new `usage_canonical` array: one independently-derived record per attempt with `observation_count` and a `quality` flag — `"single_observation"` (the expected case, given the research above), `"duplicate_observations"` (more than one identical observation — e.g. a redelivered event), or `"conflicting_observations"` (more than one observation with genuinely different values — flagged as a real anomaly rather than silently averaged, summed, or last-write-wins without comment). Aggregate endpoints (`providers/comparison`, `summary`) already picked one canonical row per attempt via `DISTINCT ON ... ORDER BY id DESC` before this session (fixing the multiplication bug in an earlier pass) and are unchanged — that heuristic is now known to be correct rather than merely convenient, given the cumulative-only research finding above.

Test: `tests/analytics_tests.rs::analytics_usage_canonical_flags_single_duplicate_and_conflicting_observations` (three attempts — one normal, one with a redelivered duplicate, one with two genuinely different values — asserts all three quality states and that the conflicting case's canonical value is the most recent observation, not an average or sum).

## 3. Comparison grain, duration, sample counts and percentiles

**UI need:** defensible attempt volume/success, duration, TTFT and throughput comparison.

**Evidence:** comparison uses `LEFT JOIN generation_usage` before `COUNT(*)` and all averages. Multiple usage records multiply an attempt, inflate counts and change weighting. Duration/TPS exclude synthetic timing and unsuccessful attempts; TTFT excludes synthetic and null markers but includes failures with a first-generation marker. No timing sample counts exist. TTFT is `(first_token_at - provider_attempts.timestamp)`. Streaming duration starts when `InstrumentedStream` is constructed **after** `execute()` returns, so it is not full dispatch-to-completion latency. The frontend labels all values as reported and exposes these caveats; it does not reaggregate averages or rank quality.

**Proposed extension to existing comparison:** one row per provider/model with attempt-grain counts; `{duration:{mean_ms,sample_count,definition},ttft:{mean_ms,p50_ms,p95_ms,sample_count,definition},output_throughput:{mean,sample_count,denominator},synthetic_attempts,usage_coverage}`. Select canonical usage before joining. Preserve failure-inclusive TTFT semantics explicitly or change them with a versioned definition. A true end-to-end duration needs an aligned monotonic dispatch boundary.

**Acceptance:** two attempts, one with three usage observations, still count as two. Synthetic and missing timing are excluded per metric, counts reflect each metric's actual population, and percentiles come from eligible raw observations rather than averages.

**Status (2026-09-23): implemented, with one deviation.** `providers/comparison` now selects canonical usage via a `LATERAL` join before aggregating (two attempts with three usage observations between them count as two), and adds `duration_sample_count`, `throughput_sample_count`, `ttft_sample_count`, `p50_ttft_ms`, `p95_ttft_ms`, and `synthetic_attempts`. Deviation from the proposal: fields are flat (`avg_duration_ms`, `duration_sample_count`, ...) rather than nested under `duration: {mean_ms, sample_count, definition}` — no `definition` string field exists per metric (the definitions live in this doc's Evidence paragraph and in `docs/API_REFERENCE.md` §12's prose instead of as a response field). `output_throughput.denominator` also wasn't added explicitly — the denominator (`duration_us`) is stated in prose, not returned as data. Tested in `tests/analytics_tests.rs::analytics_provider_comparison_does_not_multiply_attempts_with_multiple_usage_rows`.

## 4. Cost and pricing coverage

**UI need:** estimated charges, provider/model breakdown, pricing coverage and provenance.

**Evidence:** `cost_records` has a writer with configured per-1K prompt/output prices, but no read route exposes it. A missing row does not prove zero price. Current usage finality issues also affect correctness of totals.

**Proposed:** `GET /v1/analytics/costs?from=&to=&bucket=&provider=&model=` returns scoped `{currency,estimated_token_charge,billed_cost:null,priced_attempts,unpriced_attempts,eligible_attempts,pricing_source,pricing_version,series,breakdowns}`. Explicit configured zeros count as priced with a zero estimated charge; missing prices yield unknown cost. No fabricated cached-token discounts. Do not call local inference free or estimated charges provider bills.

**Acceptance:** absent price, explicit zero, positive price, different currencies and unknown usage yield distinct states. Repeated usage updates do not create repeated charges in the aggregate.

**Status (2026-09-23): implemented, scoped down from the full proposal.** `GET /v1/analytics/costs?provider=&model=` — see `docs/API_REFERENCE.md` §14. Returns `{currency, estimated_token_charge, billed_cost: null, priced_attempts, unpriced_attempts, eligible_attempts, pricing_source, breakdowns}` as proposed, with the priced/unpriced/eligible distinction intact. **Not implemented**: `from`/`to`/`bucket` date-range scoping or a `series` field — this is a whole-history summary only (no bucketing machinery existed yet when this was built; item 1's summary endpoint now has that machinery and a follow-up could extend costs to share it). Also not implemented: `pricing_version` — no versioning concept exists for the static `config.pricing` table, so only `pricing_source` (a fixed descriptive string) is returned. `currency` is always `"USD"` (the writer hardcodes it; there's no per-deployment currency setting to read back), so "different currencies yield distinct states" isn't exercised. Tested in `tests/analytics_tests.rs::analytics_cost_summary_distinguishes_priced_from_unpriced_attempts`.

## 5. Request-detail provenance and timeline boundaries

**UI need:** route rationale, structured errors, choice-separated content and accurate attempt spans.

**Evidence:** detail omits routing decisions/rejections, cost records, separate error rows/tags, attempt start/end timestamps, generation IDs/choice IDs and raw response bodies. `GenerationContent` currently combines content deltas at attempt level, so a read-only addition alone cannot recover missing choice identity. The timeline does not have pagination. The frontend preserves each returned generation row and annotates this limitation.

**Proposed extension:** `attempts` include `started_at,finished_at,duration_definition`; `generations` include stable ID, choice index when captured and terminal/partial status; separate `routing`, `errors`, `costs` and their provenance. `GET /.../timeline?after=<cursor>&limit=1000` returns `events,next_cursor,complete` with stable ordering and original timestamps. Do not infer TCP connection time from response-header time.

**Acceptance:** local failure → cloud recovery shows both spans and rejection evidence; concurrent choices remain distinguishable; cancelled output remains partial; paginated events contain each original sequence exactly once. Missing capture stays explicit. Frontend currently bounds responses at 8 MiB, displays 100 exact events/page and exports the complete returned timeline within that bound.

**Status (2026-09-23): fully implemented, including the choice-ID piece.** Request detail now includes `attempts[].started_at/finished_at/duration_definition` (migration `005_attempt_finished_at.sql` adds the `finished_at` column — it didn't exist before, only `duration_us` did), plus new top-level `routing`, `errors`, and `costs` arrays. `GET /.../timeline?after=<cursor>&limit=1000` returns `{events, next_cursor, complete}` exactly as proposed, ordered by `(attempt_number, sequence)`.

**Choice-ID piece (initially deferred, then done in a follow-up pass):** this needed the write-side change the Evidence paragraph called for — `GenerationContent` previously merged every choice's content into one accumulator with no index at all. `InstrumentedStream` now accumulates content, reasoning, and tool calls per choice index (`ProviderEvent::ContentDelta`/`ToolCallDelta` already carried an `index` field; it just wasn't used for this), and emits one `GenerationContent` event per choice on both the clean-completion and mid-stream-error paths. New migration `006_generation_choice_index.sql` adds `generations.choice_index` (existing rows default to `0`, the only value that ever existed before `n > 1` support) and `generations.status` (`'complete'`/`'partial'` — the "terminal/partial status" the proposal also asked for). `generations.id` (already a `BIGSERIAL` primary key) is now exposed in the API response as the "stable ID" the proposal asked for. Reasoning and the raw response body remain attached only to `choice_index = 0`'s row — reasoning has no per-choice index in the provider-event model, and there is one raw body per non-streaming attempt, not one per choice.

Tests: `tests/analytics_tests.rs::analytics_request_detail_includes_attempt_spans_routing_errors_and_costs` (routing/errors/costs sections), `::analytics_timeline_cursor_pagination_returns_each_event_exactly_once` (timeline pagination), `::analytics_request_detail_exposes_stable_id_and_choice_index_per_generation` (two choices read back with distinct stable IDs and correct `choice_index`/`reasoning_content` attribution), and — exercising the write side directly through the real request pipeline rather than by hand-constructing events — `tests/audit_contract_tests.rs::telemetry_emits_separate_generation_content_per_choice_for_n_greater_than_one` and `::telemetry_preserves_partial_content_per_choice_on_mid_stream_error` (an `n > 1` stream that fails mid-stream still produces two `status: "partial"` generation events, one per choice, not one merged one).

## 6. Request-list pagination and filters

**UI need:** stable browsing under concurrent inserts and real date/application/tag search.

**Evidence:** list orders only by `received_at DESC` with offset pagination and no total. Supported filters are exact requested/resolved model, final serving provider, and success. The UI keeps visible pages stable and polls a separate first-page query for a new-row notification; no undocumented filters are sent.

**Proposed extension:** bounded keyset pagination ordered by `(received_at DESC, request_id DESC)` with `{requests,next_cursor,as_of}` plus UTC from/to, an allowlist of sort fields, optional application/task/tag filters with documented exact-match semantics. An attempted-provider filter must be separate from serving-provider.

**Acceptance:** equal timestamps and concurrent new inserts neither duplicate nor omit rows during a cursor traversal; filters are honored in queries, invalid sorts rejected, and pending requests remain distinguishable from failure.

**Status (2026-09-23): implemented, with one deviation.** `GET /v1/analytics/requests` now returns `{requests, next_cursor, as_of, limit}` with `(received_at DESC, request_id DESC)` keyset pagination via an opaque `cursor` param, plus `from`/`to`, `application`, `task`, `tag`, and `attempted_provider` (kept separate from `provider`/serving-provider, as required). This is a **breaking change**: `offset` is gone. Deviation from the proposal: there is no sort-field allowlist / "invalid sorts rejected" — the ordering is fixed at `(received_at DESC, request_id DESC)` with no caller-selectable sort at all, so there's nothing to validate or reject (a fixed order was judged sufficient for the UI's actual need — stable traversal — rather than building configurable sorting nobody asked for yet). `pending` vs `failure` distinguishability was already available via `success` being `null` vs `false` and is unchanged here. Tested in `tests/analytics_tests.rs::analytics_requests_keyset_pagination_is_stable_under_concurrent_inserts` (seeds a tied-timestamp pair plus two older rows, fetches page 1, inserts a new newer row, fetches page 2 via cursor, and asserts no duplication/omission and that the new row doesn't leak into the continuation) and `::analytics_requests_supports_attempted_provider_application_task_and_tag_filters`.

## 7. Recovery endpoint scope

**UI need:** reliable recovered-request samples and separately scoped reliability rates.

**Evidence:** `/fallbacks` uses `LIMIT 200` **after joining failed attempts**. This caps rows, not distinct requests, despite the API documentation's description. A request may be cut off at the boundary; statuses other than success, including unfinished rows, qualify. No attempt number or received-at timestamp is returned. Distinct request count within the returned sample is safe; overall failure/fallback rate is not available.

**Proposed extension:** select 200 parent requests first, then return their full attempt chain with `sample_scope`, `truncated`, timestamp, attempt number and status. Keep unrecovered failures and fleet denominators in an independent summary contract.

**Status (2026-09-23): implemented as proposed.** `/fallbacks` now selects up to 200 distinct requests first, then each one's full attempt chain (`{request_id, succeeded_provider, attempts: [{attempt_number, timestamp, provider, model, status, error_code, error_message}]}`), plus top-level `sample_scope` and `truncated`. An independent fleet-wide fallback-rate summary contract (the proposal's last sentence) was **not** added — that's a distinct future contract, not folded into this endpoint. Tested in `tests/analytics_tests.rs::analytics_fallback_analysis_reflects_a_failed_then_succeeded_request`.

**Acceptance:** 200 requests with several failed attempts return complete chains, not 200 joined rows. Same-provider retry, same-provider model switch, provider switch and unrecovered error have distinct counts.

## 8. Persistence health and authentication

**Evidence:** `/health` reports provider status, treating unknown health as acceptable. It does not query telemetry persistence. The writer's fallback replay is not a pre-write journal. No auth middleware is registered in `src/server/mod.rs`; optional Authorization examples are not evidence of authentication. A missing analytics pool returns 503; a query failure with an existing pool returns **500 analytics_query_error**, not necessarily 503.

**Proposed:** a read-only persistence status contract with explicitly observed writer state, last acknowledged flush, pending/dropped counts and observation timestamp. Any public deployment needs a separately implemented access-control boundary.

**Acceptance:** healthy inference with unavailable persistence remains distinguishable; query failure is not presented as no traffic; unknown writer state is not a fabricated capture guarantee. The added frontend binds to loopback by default and does not start, reconfigure or publish the Rust gateway.

**Status (2026-09-23): persistence-health half implemented; auth explicitly declined.** Per the user's direction, this is a personal, single-user deployment never exposed beyond loopback — auth is out of scope by decision, not deferred pending a future call.

`GET /v1/analytics/persistence` returns `{mode, healthy, channel: {capacity, pending}, last_flush_at, last_flush_ok, consecutive_flush_failures, fallback_log_pending, dropped_events_total}`. `mode` is one of `"database"`/`"unavailable"`/`"disabled"` — genuinely observed writer state, not inferred from the absence of errors. `healthy` is deliberately narrow: `true` only when `mode == "database"` and the last flush succeeded and nothing is sitting in the fallback log, so "unavailable" and "disabled" both read as unhealthy for data-capture purposes even though neither is throwing errors. `channel.pending` is read live from the `mpsc::Sender` (`max_capacity() - capacity()`), not tracked separately, so it can't drift from reality. `dropped_events_total` is incremented at every `try_send`-full call site (`AppState::emit_telemetry` and `InstrumentedStream`'s internal `emit`), not just one of them — a new shared `TelemetryHealth` handle (`src/telemetry/health.rs`) threads through both. Unlike every other `/v1/analytics/*` endpoint, this one does not require `analytics_pool` and never 503s for a missing one, since it reports on the write-side pipeline, which is independent of the read-side pool — satisfying "query failure is not presented as no traffic" by construction (there's no query to fail).

Tests: `tests/api_tests.rs::test_persistence_health_endpoint_works_without_analytics_pool` and `::test_persistence_health_counts_dropped_events_and_channel_backlog` (a capacity-1 channel, three sends, asserts exactly 2 dropped and the backlog reported), plus `tests/db_verification_tests.rs::writer_health_reflects_a_real_successful_flush` — a real flush against a real Postgres, checked through the same `Arc<TelemetryHealth>` handle the writer updates in place, confirming `last_flush_at`/`last_flush_ok` actually reflect what happened rather than a static default.
